# 0007. The secrets controller holds no secret permission

- **Status:** Accepted
- **Date:** 2026-09-13
- **Phase:** 6

## Context

External Secrets usually runs with one IAM role that can read every secret it might
be asked to sync. Any SecretStore in any namespace can then use that reach, and
CloudTrail attributes every read to one identity.

## Decision

The controller's role can do exactly one thing: assume roles named
`idp-<environment>-svc-*`. Each service's SecretStore names that service's role, which
can read only `idp-<environment>/<service>/*`. Cluster-wide stores and cluster-wide
ExternalSecrets are not installed as CRDs, and Kyverno refuses a store naming another
service's or environment's role, static credentials, or chained roles.

## Consequences

- A read of a secret is authorised by, and attributed to, the service it belongs to.
- Three independent layers separate services: IAM, admission policy and Git review.
- One role per service per environment multiplies IAM objects, all generated by
  Terraform from the service registry.
- Role chaining from a Pod Identity session needs `sts:TagSession` on every service
  role's trust policy, because the session tags are transitive.
